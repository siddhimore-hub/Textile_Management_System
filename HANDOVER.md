## Added in this round: product-led production runs (automated stage chain)
Production now starts from a **catalogue product**, not from free-typed fabric names. Page: **Production > Make a product** (`/runs`, `frontend/src/pages/Runs.jsx`).

When Finishing is completed the run closes and **rolls are cut automatically** (max `ROLL_LENGTH_M`=100 m each, env-overridable), named after the product: `P-0001-PR0003-02` (product code, run code, number). Rolls start QC `pending`; once QC passes them they appear under **Finished Products** and in **Stock by product**.

## Gotchas
- Invoice rule (M3/M4): one document per transaction. A dispatch raises its SALE invoice immediately (unique by `invoices.dispatch_id`); a goods receipt raises a PURCHASE bill (unique by `invoices.receipt_id`). `POST /payments` only updates the sale invoice's paid/unpaid status (dedup by `invoices.dispatch_id`); partial payments are allowed and show as `pending`/`partial` in `GET /pending-payments`. `POST /payments` accepts `dispatch_id` (preferred) or a legacy `invoice_id`. `GET /invoices` lists both kinds (`kind: sale|purchase`); a purchase bill is `na` when its total is 0 (no unit price given).
- Stock-production jobs are normal jobs on an internal order (buyer `Internal Stock`, `orders.is_internal=1`). They are hidden from `/orders/assignable` and excluded from `/finance/receivables`; everything downstream (stages, QC, rolls, finished stock) is unchanged.
- Compatibility: a `fabric_type` with no rule accepts any yarn (e.g. `voile`); a fabric with several yarn families is a blend and the `blend_ratio`s must sum to ~100% (400 `BAD_BLEND_RATIO`); wrong yarn -> 400 `INCOMPATIBLE_YARN`. Rules are editable from the Products page. Seed: material 1 = cotton, material 3 = polyester.
- Products: a product's fibre composition must total 100% (`BAD_COMPOSITION`) and every BOM yarn must suit the fabric (`INCOMPATIBLE_YARN`). Products used on an order are deactivated, not deleted. The catalogue page also holds the fabric-yarn rules.
- Cart orders: `POST /orders` with `lines` snapshots price/composition/BOM into `order_lines` (so later price edits do not change old orders) and sums the BOM into `order_requirements`. `orders.product_id` stays NULL for multi-product orders; a roll's product comes from its `order_line_id` (falling back to `orders.product_id` for legacy single-product/stock orders).
- Fulfilment: `stock_allocations` reserves QC-passed, undispatched stock (oldest open order line first) via `reallocate`, called after inspections, order creation, dispatch and (stock-production) completion. Line status is derived: `fulfilled` (dispatched >= ordered), `available` (fully reserved), `partial` (some reserved), `pending` (nothing reserved). Cross-order dispatch is allowed only within what was reserved for that line (`NOT_ALLOCATED`), and never more than ordered (`EXCEEDS_ORDER`).
- `ORDER_COMPLETE` uses rolls (QC-passed), so a spinning order is only blocked once all its qty_metres are rolled, not merely produced.
- Order status is derived, not stored (`backend/src/lib/orderStatus.js`) from the whole pipeline including finished-stock fulfilment, so an order met from stock (even stock rolled for another order) is `ready_to_ship`, not "not started". Partial states: `partially_fulfilled` (some reserved), `partially_dispatched` (some shipped).
- Rolls now come only from completed **finishing** jobs (`POST /rolls` needs a `job_card_id` whose stage is `finishing` and status `done`, and `metres` <= the batch's remaining material). The old shortcut of rolling straight from any running job is gone.
- `GET /jobs/available?stage=<stage>` shows material from completed jobs of `<stage>` that no later job consumed (for `finishing`, minus metres already rolled). Roll metres are the only consumption of a finishing batch.
- Stock `reserved` = required by orders minus yarn already issued; `available` = on hand minus reserved; `low` uses available.
- `npm run db:reset` deletes `backend/data/mill.db`; seed data comes from `db/seed.sql`. Existing databases keep their data and get new tables on next start; users that predate login get the default password.
- Payroll: running it early in a month inserts a row per worker (unique per month), so later runs skip them. Run payroll at month end, or delete the rows first.
- Do not `pkill -f "node src/index.js"` from a script that contains that text; use the process id.
- Vite proxies `/api` to port 4000 in dev; there is no production server config yet.
- Vehicle number must look like TN09AB1234 (see dispatch validation).
- Tests: backend tests need `backend/test-support/helpers.js` (kept out of `test/` so Node does not run it as a test).
